# 存储、传输与资源限制

给 AI 代理的模块细则（由根目录 AGENTS.md 索引）。读取名额、并发上限、传输性能、秒传、内容类型识别、Telegram 分片上传、GC。

- 文件读取名额（`TransferSlots`，下载、预览、播放、S3 读取共用）由「系统设置 → 下载与资源」的 `transfer_concurrency`／`bucket_concurrency` 配置（`ResourceSettings`，1–32，启动参数 `--transfer-concurrency`／`--bucket-concurrency` 只作默认值，旧配置缺项时用启动值补齐），默认 8／6，`effective()` 只按内存收紧（每路 24 MB，最多占三分之一；不足 512 MiB 或未知时 3 路），不看 CPU 核数——「自动」因单核选了低资源档时读取仍按设置生效，只有管理员明确选择「低资源」才封顶 8 路，每账号不再减半，`app.apply_resources` 保存后立即生效；1.38 之前保存的旧默认值 4／2 由 `ResourceSettings.config` 一次性升级（settings `offline.resources.read_defaults`）。后台读取（本机缓存整文件，请求头 `X-Tessera-Background: cache` → `Scope.background` → `TransferSlots.slot(background=True)`）最多占「名额 − 1」、排队等待 3 倍时间（90 秒，须短于反向代理的首字节超时），从 1 MiB 起步（1→4→8 MiB，不用前台的 256 KB 起步，也不直接取整个后端窗口，否则存储慢时首字节要等整个 8 MiB）；本机缓存的 Worker 收到 503 + Retry-After 时原地等待同一段，不计入失败重试；离线下载写入内存中的分段（`upload_part(..., buffered=True)`）不占这些读取名额，只受上传名额约束；播放与预览不要加这个标记。
- 并发上限（`ResourceSettings.validate`）：离线下载 `concurrency` 1–16（内存 1 GiB 以上 `effective` 按每任务 `DOWNLOAD_MEMORY` 64 MB、最多占检测内存的 `download_memory_percent`（10–80，默认 60）封顶；64 MB 来自实测：直链任务正在写入时约 48 MB、排队等写入时约 16–20 MB，另留视频转封装与分配器余量，改下载或写入流程后重新测；这个上限只看内存、不看 CPU 核数——单核但内存充足的机器同样按比例计算，只有内存不足 1 GiB 或无法检测时沿用 1–4 档）；M3U8／YouTube（`OfflineDownloads._exclusive`）同时最多 `video_concurrency` 个（1–4，默认 2，`effective` 的 `ffmpeg_concurrency`：内存不足 1 GiB 时 1 个、不超过 `concurrency`），调度器与 `_yield_plan` 按这个数计数；`platform_max_mib`（平台临时缓存，磁盘）按设置生效，不随资源档位收紧、读取 1–32、写入分片 1–32、网页分段 1–16、网页同时上传文件 1–8（`uploads.tsx` 的 `uploadLimits` 同步上限）、缩略图读取 1–32。
- 传输性能：前端大文件（>64 MB）按服务端给出的 16 MB 分块上传，分段并发与同时上传的文件数由管理员在「下载与资源」配置（`web_part_concurrency` 默认 4、`web_file_concurrency` 默认 2），网页经 `GET /api/user/v1/upload-config` 读取（`web/src/user/uploads.tsx` 的 `uploadLimits`，每分钟最多刷新一次），不要再写死常量；写入存储由 `BlobEngine.upload_slots`（`Limiter`，`upload_concurrency` 默认 4，每个在途分片约 32 MB）与 `upload_rate`（`RateLimiter`，`upload_kib`，0 不限速）全局限制，每个 Bot 两次发送的最短间隔是 `bot_interval_ms`（`ConfiguredBlobStore.set_bot_interval` 同步到已建立的 `BotPool.min_interval`），都在 `app.apply_resources` 中随保存立即生效；服务端加解密放在 `asyncio.to_thread`，`BlobEngine.stream` 用 `read_ahead` 个窗口的流水线预读（`tests/test_download_pipeline.py`）。浏览器播放视频会连发开放式 Range 并很快中断大部分请求，所以远端读取的窗口从 256 KB 起每次放大 4 倍到后端窗口（Telegram 为 8 MB，见 `ConfiguredBlobStore.read_window`），预读深度随已交付窗口数逐步加深；`PooledTransport` 分段读取响应体，请求被取消时停止下载并丢弃连接。Telegram 的阻塞 HTTP 请求在 `telegram/client.py` 的专用线程池 `in_network_thread`（64 线程）里执行，不要改回 `asyncio.to_thread`：默认线程池只有「CPU 核数 + 4」个线程并与解密共用，小机器上几个长下载窗口就会让播放器跳转（如读取末尾的 moov）排队，表现为缓存了很多仍不能播放（`tests/test_network_threads.py`）。不要改回“一开始就按大窗口并行预读”，否则每个被中断的请求都会白白下载十几 MB。调大并行度前先估算内存：上传约 并行块数 × 2 × 16 MB，下载约 (read_ahead+1) × 读取窗口。
- 秒传（`tgdrive/fingerprint.py`、`ObjectService.instant_put`、`web/src/fingerprint.ts`）：指纹是 16 MiB 分块 SHA-256 的哈希树，算法是对外约定（见文档站 `/files/instant`），服务端和前端必须保持一致，改动会让已有指纹失效。指纹存在 `blobs.fingerprint`，写入时由 `put_part` 顺带计算（不重读数据）；分段上传只有除最后一段外每段都是 16 MiB 整数倍才有指纹。命中只在调用者自己的桶、授权前缀内查找，回收站前缀 `.tgdrive/` 不参与。新增会创建 Blob 的写入路径时要保证走 `put_part`，并在 `finalize` 后设置指纹。写入后合并：`put_object`（`small=False`）与 `complete_multipart` 调 `_commit_blob(..., dedupe=True)`，在提交事务内用 `_duplicate_blob` 找同桶同指纹的完整 Blob（范围同秒传，含私密、不含回收站与系统区），找到就改引用它、保留对象自己的 ETag，随后删除刚写入的 Blob（分段上传先把 `uploads.blob_uuid` 改指向它）；缩略图因此按内容共用。网页上传 ≥64 KiB 才做秒传探测（`INSTANT_MIN_SIZE`），同批同指纹的文件经 `sameContent` 排队，第一个上传完成后其余再探测秒传。测试中需要不同 Blob 时请写入不同内容。
- 文件类型以内容为准（`tgdrive/sniff.py`，schema v34 的 `blobs.sniffed`）：`BlobEngine._put_part` 写第 1 段时用开头 `HEAD_BYTES`（8 KiB）调用 `sniff`，记录「把握程度:类型」（exact／text／zip／ole／unknown／empty）；`ObjectService._commit_blob` 用 `sniff.resolve` 与上传方给出的类型合并（exact 直接采用，但同一容器的音频声明与相机 RAW 保留；text 保留文本类声明或按文件名推断文本类型；unknown 时声称有明确格式却认不出的改为通用二进制），覆盖网页上传、`/api/v1`、离线下载、秒传与解压等所有写入。S3 的 PUT／分段完成（`declared_type=True`）与复制（`declared=True`）保留客户端声明的类型。没有记录的旧数据沿用原类型。改名不改类型。类型分类（`filekinds.py` 的 `_RULES` 与前端 `getFileKind`，两边一致）改为具体的 MIME 优先：扩展名只在 MIME 缺失或通用二进制时生效，例外是音频扩展名配音视频 MIME（容器相同）与文本 MIME 下按扩展名细分源代码。测试里给媒体文件写占位内容时要带上对应的文件头（`tests/test_assistant.py` 的 `MEDIA_MAGIC`），或用 `declared_type=True`；回归 `tests/test_content_type.py`。
- Telegram 分片上传（`telegram/store.py` 的 `TelegramBlobStore.put`）：限流、5xx、网络、凭据与其他拒绝（400 等）都换 Bot 重试，每个 Bot 都试过后等 `RETRY_PAUSE` 再从头轮换（只有一个 Bot 时也会重试），最多 `MAX_UPLOAD_ATTEMPTS` 次；大文件有几百个分片，不能让一次偶发拒绝使整个文件失败。其他拒绝的说明写入日志（不含 token）。回归 `tests/test_telegram_store.py`。
- GC 失败队列跨重启保留，8 次失败后暂停。Telegram 删除仅在明确返回 400「message to delete not found」时按幂等成功处理，不能把普通 404、频道、凭据或权限错误当成清除成功。`maintenance.status` 的 `gc_failures` 通过 SQL 聚合为固定的原因、数量与建议，不暴露分片引用或原始错误；维护页待清除总数包含暂停项，「重新尝试」先重新入队再立即执行一轮，运行中禁止重复提交。回归 `tests/test_gc_failures.py` 与 `tests/test_telegram_store.py` 使用替身，不连接数据库或 Telegram。
